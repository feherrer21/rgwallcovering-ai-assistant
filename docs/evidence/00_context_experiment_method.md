# Context Artifact Experiment — Method

**Task:** T0.1 / T0.3 (`05_tasks.md`)
**Subject module:** `agent_core/retrieval.py` — fixed in `04_plan.md` **before**
any result was seen.

## What is being measured

Whether a `CLAUDE.md` context artifact changes the quality of generated code,
and in what specific way. The case requires before-and-after evidence; this
file records the procedure so the comparison can be challenged.

## Controlling for conversational context

A naive version of this experiment would have me generate the "before" module
myself, in the same session where the specification was written. That session
already carries the corpus findings, the trust-tier design and the relevance-
floor rationale — so the "before" output would be shaped by all the context
that `CLAUDE.md` is supposed to supply, arriving by a different route. The
diff would come out small and the honest conclusion would be "the artifact
adds little", which would be an artefact of a badly designed experiment rather
than a finding.

**Control applied:** the "before" module was generated by a subagent with a
cold context window — no access to this conversation, no access to the
specification, and instructed not to read any file in the repository. It
received only the task description reproduced verbatim below.

**Residual confound, stated:** the "after" generation runs in the main session
and therefore *does* carry conversational context in addition to `CLAUDE.md`.
The comparison is consequently **cold-with-nothing vs warm-with-artifact**,
which overstates the artifact's effect. The mitigation is qualitative: the
analysis in `context_artifact_effect.md` attributes each difference to either
the artifact or the session context, and differences that cannot be
confidently attributed are labelled as such rather than counted.

A cleaner design — a second cold subagent given only `CLAUDE.md` — was
considered and rejected for time. Recorded as a limitation, not as a
non-issue.

## The prompt (identical for both runs, verbatim)

> Write `agent_core/retrieval.py` for a Python RAG chatbot that answers
> questions on the website of RG Wallcovering, a wallpaper and painting
> company in Providence, Rhode Island.
>
> A separate ingestion script has already fetched the company's website pages
> and blog posts, split them into text chunks, embedded them, and written the
> results to `data/index/`. Your module is the retrieval half: given a user's
> question, it embeds the question and finds the most relevant chunks from
> that index, so the chatbot can answer from them.
>
> Use `fastembed` with the `BAAI/bge-small-en-v1.5` model for embeddings. The
> index on disk consists of a numpy array of chunk embeddings plus a JSONL
> file of the corresponding chunk records (each record has the chunk text and
> metadata about which page it came from).
>
> Provide the public function(s) the rest of the application will call to
> search the corpus. Include reasonable error handling and docstrings.

The "before" run additionally carried the isolation instruction (do not read
any repository file), which is a property of the control, not of the task.

## Artifacts

| File | What it is |

informed by whichever choices survived scrutiny.
